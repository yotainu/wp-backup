# WP pCloud Backup 設計書

作成日: 2026-10-24
改訂: 2026-10-25（ビルダーレビューと依頼者回答を反映）
状態: ドラフト（承認待ち）

## 1. 目的と背景

BlogVault（年額約2万円）を自作の WordPress プラグインで置き換え、保存先には既存の pCloud アカウントを使う。
対象は約80サイト。復元機能は必須ではなく、「全ファイルとデータベースが指定した周期で pCloud に残っている」ことが達成目標。

成功の定義:
- 80サイトすべてで、設定した周期どおりにバックアップが pCloud に届いている
- 失敗したら、見回らなくてもメールで分かる
- BlogVault を解約できる

## 2. 対象環境

| 区分 | サイト数 | 規模 | サーバー | SSH | 備考 |
|---|---|---|---|---|---|
| A | 約72 | 100MB〜3GB | heteml（共用） | 可 | 大多数 |
| B | 3〜4 | 100MB〜5GB | さくらレンタルサーバー（共用） | 不可 | コントロールパネルに cron あり |
| C | 3〜4 | 約5GB | heteml | 可 | |
| D | 1 | 約40GB | ColorfulBox VPS | 可 | **本プラグインの対象外**（後述） |

pCloud アカウントは1つ。米国リージョン（my.pcloud.com）なので API ホストは `api.pcloud.com`。

## 3. 作るもの（2つ）

### 3.1 WordPress プラグイン「WP pCloud Backup」（区分 A・B・C 向け）

全ファイル + データベースをまるごと圧縮し、pCloud の日付フォルダに保存する。本設計書の主題。

### 3.2 VPS 用バックアップスクリプト（区分 D 向け）

40GB サイト1つのために、rclone + mysqldump + cron のシェルスクリプトを用意する。
PHP の実行時間制限を受けず、`rclone sync` で変更分だけ送れるため、超大規模サイトはこちらが適切。
本設計書では概要のみ記し、詳細は別途（プラグイン完成後に着手）。

## 4. ゴール / 非ゴール / アンチゴール

**ゴール**
- 全ファイル（バックアップ起点フォルダ以下すべて。5.3 参照）と DB の完全バックアップを周期的に pCloud へ保存
- 周期・世代数・pCloud トークン・通知メールを管理画面で設定できる
- 共用サーバー（PHP 実行時間 30〜60秒、シェル不可）で 5GB のサイトを完走できる
- 失敗時にメール通知
- 古い世代の自動削除
- 80サイトに同じ手順で導入できる（設定項目は最小限）

**非ゴール（やらない）**
- 管理画面からのワンクリック復元（復元は「pCloud からフォルダを落として展開し、SQL を流し込む」手作業。手順書は README に書く）
- 差分・増分バックアップ
- 80サイトを横断する集中管理ダッシュボード
- pCloud 以外の保存先
- マルチサイト（ネットワーク）対応
- サイト外部からの死活監視（VPS から pCloud のフォルダ日付を見回る監視スクリプトなど）。依頼者が不要と判断。停止検知はプラグイン内の仕組み（8.3）に限る

**アンチゴール（これが起きたら失敗）**
- バックアップが静かに止まっていて、気づいたら数ヶ月分ない
- バックアップ処理が原因でサイトが重くなる、落ちる
- バックアップファイルや pCloud トークンが外部から取得できる
- 壊れたアーカイブが「成功」として保存されている

## 5. ユーザー（管理者）から見た動き

### 5.1 初回設定

**アクセストークンの取得（最初の1回だけ）**

1. pCloud の「My Apps」（docs.pcloud.com/my_apps）でアプリを1つ登録し、Client ID / Client Secret を得る。redirect URI は登録しない
2. 最初のサイトのプラグイン「接続」タブで Client ID / Client Secret を入力し「認可コードを取得」を押す。pCloud の認可画面（`https://my.pcloud.com/oauth2/authorize?client_id=…&response_type=code`、redirect_uri なし）が新しいタブで開き、「許可」を押すと**画面上に認可コードが表示される**（redirect_uri を省略した場合の pCloud 公式の挙動）
3. そのコードをプラグインに貼り付けて「接続」。プラグインが `oauth2_token` でアクセストークンに交換し、暗号化して保存する。Client Secret はこの交換にしか使わないので保存しない
4. 接続後、「接続」タブに「このトークンを他のサイトにも使う」ボタンがあり、押すとトークンを一度だけ表示する（コピー用）。pCloud のアクセストークンは期限なし（公式ドキュメント明記）なので、80サイトで同じトークンを使い回す

redirect_uri を使わない理由: pCloud 側に80サイト分の redirect URI を登録できるか、同じアプリで認可を繰り返したとき古いトークンが無効化されないかが公式ドキュメントから確認できない。トークンを1回だけ取得して配る方式ならどちらの不確実性も避けられる。

**2サイト目以降**

1. プラグインを有効化し、「接続」タブの「アクセストークンを貼り付け」欄にトークンを入れて保存（または `wp-config.php` に `define('WP_PCLOUD_BACKUP_ACCESS_TOKEN', '…');` を書く。定数があれば管理画面の入力欄は「定数で設定済み」表示になりロックされる）
2. プラグインは保存時に `userinfo` を呼んでトークンの有効性を確認し、アカウントのメールアドレスを表示する
3. 保存先フォルダ名（既定値: サイトのホスト名）、周期、世代数、通知メールを設定して保存
4. 「今すぐバックアップ」で1回手動実行し、pCloud にファイルが届くことを確認

### 5.2 日常

- 何もしない。設定した周期で自動的に走る
- 失敗したときだけメールが来る
- 管理画面に「最終成功日時・直近の実行履歴（最新20件）・次回予定」が表示される

### 5.3 バックアップの起点フォルダ

「全ファイル」の起点は WordPress の設置フォルダ（`ABSPATH`）ではなく、**サイトの公開ルート**とする。依頼者の80サイトのうち1サイトは WordPress 本体をサブフォルダに置き、ドメイン直下から見せる構成であり、ドメイン直下の `index.php`・`.htaccess`・WordPress 外の静的ファイルも含めて保存したいため。例外扱いにせず全サイト同じ規則にする。

既定値の決め方（自動検出）:
- `site_url()` のパス部分が `home_url()` のパス部分より深い場合（例: site_url が `/wp`、home_url が `/`）、その差分だけ `ABSPATH` から上に辿ったフォルダを起点とする
- そうでなければ `ABSPATH` を起点とする
- 検出結果は「設定」タブに「バックアップ起点フォルダ」として表示し、手で変更もできる。起点より上のフォルダや、`ABSPATH` を含まないフォルダは指定できない（誤って契約アカウント全体を拾わないため）
- manifest.json に起点フォルダの絶対パスと `ABSPATH` の両方を記録し、復元時にどこへ戻すか分かるようにする

## 6. 設定項目

| 項目 | 選択肢 / 形式 | 既定値 |
|---|---|---|
| pCloud アクセストークン | 貼り付け欄（保存後は表示しない）。または認可コードから取得（Client ID / Secret 入力 → コード貼り付け） | 空 |
| pCloud 接続状態 | 接続済み（アカウントのメール表示） / 未接続 | 未接続 |
| バックアップ起点フォルダ | サーバー上の絶対パス（5.3 の規則で自動検出、変更可） | 自動検出 |
| 保存先ルートフォルダ | pCloud 上のパス | `/WPBackup` |
| サイトフォルダ名 | 文字列 | サイトのホスト名（例 `example.com`） |
| 周期 | 毎日 / 3日おき / 毎週 / 2週間おき / 毎月 | 毎週 |
| 実行開始時刻 | 時刻（サイトのタイムゾーン） | 03:00 |
| 保持世代数 | 1〜30 | 3 |
| 通知メール | メールアドレス（カンマ区切りで複数可） | 管理者メール |
| 成功時もメールする | ON / OFF | OFF |
| 除外パス | 1行1パス（起点フォルダからの相対） | 下記の既定除外 |
| 分割サイズ | 10 / 25 / 50 / 100 MB | 25MB |
| 1回あたりの処理時間上限 | 秒 | 20 |
| 起動方式 | WP-Cron を使う ON/OFF、外部 cron 用 URL の表示と鍵の再発行 | WP-Cron ON |
| 自動更新 | ON / OFF（GitHub Releases から新バージョンを自動適用。12.1 参照） | ON |

既定除外: プラグイン自身の作業フォルダ、`wp-content/cache`、`wp-content/uploads/backup*`（他のバックアッププラグインの残骸）、`wp-content/updraft`、`wp-content/ai1wm-backups`、`.git`、`node_modules`。

**`wp-config.php` の定数による事前設定**: 80サイト導入の手間を減らすため、以下の定数があれば設定画面の値より優先し、画面上は「定数で設定済み」としてロック表示する。
`WP_PCLOUD_BACKUP_ACCESS_TOKEN`、`WP_PCLOUD_BACKUP_NOTIFY_EMAIL`、`WP_PCLOUD_BACKUP_ROOT_FOLDER`（pCloud 側ルート）、`WP_PCLOUD_BACKUP_SCHEDULE`、`WP_PCLOUD_BACKUP_KEEP`（世代数）。

## 7. バックアップの中身と pCloud 上の配置

```
/WPBackup/
  example.com/
    2026-10-24_030000/
      manifest.json          ← 日時、WordPress/PHP バージョン、起点フォルダ、ファイル数、合計サイズ、各パートの SHA-1 と SHA-256、DB テーブル一覧
      database.sql.gz        ← データベース内の全テーブルの SQL ダンプ
      files.zip.001          ← ファイル一式の ZIP を 25MB ごとに分割したもの
      files.zip.002
      ...
      files.zip.123
    2026-10-17_030000/
    2026-10-10_030000/
```

- ZIP は ZIP64 形式（4GB 超対応）。分割は ZIP 内部の仕様ではなく単純なバイト分割なので、復元時は `cat files.zip.* > files.zip` で結合して展開する（Mac/Linux/Windows いずれも標準機能で可能。手順は README に記載）
- 画像・動画・圧縮済みファイル（jpg/png/gif/webp/mp4/zip/gz など）は無圧縮で格納し、それ以外は deflate 圧縮する。共用サーバーの CPU 時間を無駄にしないため
- DB ダンプは接続先データベース内の**全テーブル**（プレフィックスで絞らない）。依頼者の環境では1データベースを複数サイトで共有していないため、プレフィックスなしのテーブルを作るプラグインのデータも取り落とさないよう全テーブルとする。manifest にテーブル一覧を記録する
- DB ダンプは `CREATE TABLE` + `INSERT`（複数行まとめ）。`wp_options` 内の一時データ（`_transient_%`）は除外する
- 日付フォルダは完了するまで `.incomplete-2026-10-24_030000` という名前で作り、manifest まで揃ってから本来の名前にリネームする。未完了フォルダは「成功した世代」として数えない
- 世代削除: 成功フォルダが保持世代数を超えたら古いものから `deletefolderrecursive`。未完了フォルダは48時間経過したものを削除

## 8. 処理の仕組み（共用サーバーで完走させる要）

### 8.1 ジョブとステップ

1回のバックアップは「ジョブ」。ジョブは複数の「ラン」（1回の PHP 実行、既定20秒）に分かれて進む。進捗は作業フォルダの `state.json` に保存し、次のランは続きから再開する。

ジョブの段階:

1. **準備** — 作業フォルダ作成、pCloud に `.incomplete-…` フォルダ作成、除外設定の読み込み
2. **ファイル一覧作成** — 起点フォルダ（5.3）を再帰走査し、対象ファイルの一覧（パス・サイズ・更新日時）を `filelist.jsonl` に書き出す。走査自体も時間上限で中断・再開可能（ディレクトリ単位で進捗を記録）
3. **DB ダンプ** — テーブルごと、1000行ずつ `SELECT` して SQL を追記。進捗は「テーブル名 + オフセット」。全テーブル終了後に gzip 圧縮（これも分割して進める）
4. **ZIP 作成** — 一覧の先頭から順にファイルを ZIP に追記していく。独自のストリーミング ZIP ライタ（純 PHP）を使う。ZIP の出力は分割サイズ（既定 25MB）に達するごとに次のパートファイルへ切り替える。進捗は「一覧の何行目まで」+「現在のパート番号と書き込み済みバイト数」
5. **アップロード** — 完成したパートから順に `uploadfile` で送る。送信は PHP の `curl` 拡張を直接使い、`CURLFile` でディスクからストリーミングする（`wp_remote_post` はボディをメモリ上に全部組み立てるため使わない）。**アップロードのランは処理時間上限の例外**とし、1パートの送信が終わるまで待つ（HTTP リクエストは途中で切れない。PHP の `max_execution_time` はネットワーク待ち時間を数えないので、CLI/cron からの実行では問題にならない）。curl 側は全体タイムアウト 600 秒、低速検知（30秒間 1KB/s 未満で中断）を設定する。送信後に `checksumfile` で **SHA-1** を照合する（米国リージョンの `checksumfile` は sha1 と md5 のみ返す。SHA-256 はローカルで計算して manifest に記録するだけ）。一致したらローカルのパートを削除する。ZIP 作成と並行はせず、「ZIP が1パート完成 → そのパートをアップロード → 次のパート作成」と交互に進める。これで作業フォルダの一時ファイルは常に最大2パート分（既定で約50MB）に収まる
6. **仕上げ** — manifest.json 作成・アップロード、フォルダを本来の名前にリネーム、古い世代の削除、履歴に記録、成功通知（ON のとき）
7. **後片付け** — 作業フォルダ内のジョブファイルを削除

### 8.2 ランの起動

3つの経路すべてが同じ「ランナー」を呼ぶ。ランナーは `state.json` を見て続きを実行する。

- **WP-Cron**: 1分ごとのイベントを登録。ジョブ実行中はイベントのたびに1ラン進める。ジョブがない時は「次回予定時刻を過ぎていれば新しいジョブを作る」だけ
- **外部 cron 用 URL**: `https://example.com/?wp-pcloud-backup=run&key=<64文字のランダム鍵>`。叩かれるとランナーを1回実行して JSON（状態）を返す。推奨は「1〜5分ごとに叩く」
- **管理画面の「今すぐバックアップ」**: ジョブを作り、ブラウザから AJAX で繰り返しランナーを呼んで進捗バーを表示する（画面を閉じても cron 側が続きを進める）

ランナーの排他制御: `state.json` 更新時にロックファイル（`flock`）を取り、取れなければ即終了。前回のランの開始から（処理時間上限 × 3）秒経っていないラン開始は無視する（連打対策）。

### 8.3 失敗の扱い

- 1ランの中でエラー（pCloud 応答エラー、ファイル読み取り失敗など）が起きたら、そのステップを最大5回まで次のランで再試行する。ネットワーク系は再試行、権限系（トークン無効 2000 番台、容量超過 2008）は即失敗
- 5回失敗、またはジョブ開始から48時間経過したら「失敗」。pCloud の `.incomplete-…` フォルダを削除し、エラー通知メールを送り、ローカルの作業ファイルを消す
- 読めないファイル（権限なし・途中で消えた）は警告として manifest に記録し、ジョブ自体は続行する。警告が1件以上あれば成功メールに含める（成功メール OFF でも警告だけはメールする）
- 「前回の成功から周期の2倍以上経っている」状態を検知したら、ジョブが走っていなくても1日1回「バックアップが止まっています」メールを送る（WP-Cron が動いていない、URL cron が止まった、などの静かな死を検知する）

### 8.4 PHP の制約への対処

- `set_time_limit(0)` と `ignore_user_abort(true)` は試みるが、効かない前提で時間上限を自分で測る（アップロード中は例外。8.1 の 5）
- 分割サイズの既定を 25MB にしたのは、日本の共用サーバーから米国の pCloud への上り速度（1〜5MB/s 程度を想定）で1パートが数十秒以内に送り切れるようにするため。Web サーバー経由（WP-Cron のループバック、外部 cron URL）の実行には Web サーバー側の応答タイムアウト（60〜120秒程度）があり、それに収める必要がある。回線が速いサーバーでは設定で大きくできる
- メモリ: ファイルは 1MB ずつストリーム読み書き。ファイル一覧は配列に持たず JSONL ファイルで逐次処理。アップロードは `CURLFile` によるストリーミング
- シェルコマンド（`exec`, `zip`, `mysqldump`）には一切依存しない。必須の PHP 拡張は `zlib` と `curl` と `openssl`（いずれも heteml・さくらの標準構成に含まれる）。有効化時にチェックし、欠けていれば管理画面に警告を出す
- 80サイトが同じ時刻に走ると pCloud 側の負荷・レート制限が心配なので、実行開始時刻に対してサイトごとの固定オフセット（サイト名のハッシュから0〜59分）を加える

## 9. セキュリティ

- **外部 cron 用の鍵**: 64文字のランダム文字列。`hash_equals` で比較。管理画面から再発行可能。URL でできるのは「ランナーを1回動かす」だけで、データの取得・設定変更は不可
- **pCloud トークン**: `AUTH_KEY`・`SECURE_AUTH_KEY` から導出した鍵で AES-256-GCM 暗号化して `wp_options` に保存。管理画面には「接続済み（アカウント: メール）」のみ表示。「接続解除」でトークンを破棄
- **Client ID / Secret**: 認可コードの交換時に一度使うだけで、保存しない
- **トークンの使い回し**: 80サイトで同じトークンを使うので、1サイトの管理者権限が奪われると pCloud アカウント全体に書き込み・削除ができる。これは pCloud の API にフォルダ単位の権限がない以上、サイトごとに認可しても同じ（どのトークンもアカウント全体に届く）。対策は「pCloud 側でバックアップ専用のアカウントを使う」ことで、README に推奨として書く。トークンが漏れた疑いがあるときは pCloud の My Apps でアプリを削除すれば全トークンが無効になる
- **トークンの表示**: 「他のサイトにも使う」ボタンで一度だけ表示する際は、`manage_options` + nonce + 直前のパスワード再確認（WordPress 標準の再認証ではなく、プラグイン側で現在のパスワードを `wp_check_password` で確認）を要求する
- **作業フォルダ**: `wp-content/uploads/wp-pcloud-backup-<ランダム16文字>/`。`.htaccess`（`Deny from all` / `Require all denied`）と `index.php`（空）を置き、nginx 環境では警告を表示。パート・ダンプファイルの名前もランダム接頭辞付き
- **管理画面**: `manage_options` 権限のみ。全フォームに nonce
- **自動更新の改ざん対策**: 更新パッケージの SHA-256 をリリースの `.sha256` ファイルと照合し、不一致なら更新を中止して通知メールを送る（12.1）
- **DB ダンプにはパスワードハッシュ等が含まれる**ため、pCloud 側のフォルダは共有しないこと、を README に明記
- **ログ**: トークン・鍵は一切ログに出さない

## 10. 通知メール

送信は `wp_mail`。件名にサイト名を含める（80サイト分を1つの受信箱で見分けるため）。

- 失敗: `[WP pCloud Backup] 失敗: example.com` — 失敗したステップ、エラー内容、再試行回数、管理画面へのリンク
- 停止検知: `[WP pCloud Backup] 停止中: example.com` — 最終成功日時、推定原因（WP-Cron 無効、URL が叩かれていない）
- 警告付き成功: `[WP pCloud Backup] 完了(警告あり): example.com` — 読めなかったファイル一覧
- 成功（ON のとき）: `[WP pCloud Backup] 完了: example.com` — サイズ、ファイル数、所要時間、pCloud パス

## 11. 管理画面

WordPress 管理メニュー「設定 > pCloud Backup」に1ページ。タブは3つ。

1. **状態** — 最終成功日時 / 次回予定 / 実行中ジョブの進捗バー / 「今すぐバックアップ」ボタン / 直近20件の履歴（日時・結果・サイズ・所要時間・pCloud パス）
2. **設定** — 6章の項目
3. **接続** — アクセストークン貼り付け欄 / 認可コードからの取得（Client ID・Secret 入力 → 認可画面を開く → コード貼り付け）/ 接続状態（アカウントのメール）/ 「このトークンを他のサイトにも使う」/ 接続解除、外部 cron 用 URL（コピー・再発行）、WP-Cron の有効状態の診断（`DISABLE_WP_CRON` の検出）、サーバー情報（PHP バージョン、時間制限、メモリ、zlib 有無、作業フォルダの書き込み可否、ディスク空き容量）

デザインは WordPress 標準の管理画面スタイルに合わせ、独自 CSS は最小限。

## 12. 技術的な決定事項

| 決定 | 内容 | 理由 |
|---|---|---|
| 言語・依存 | PHP 7.4 以上、WordPress 6.0 以上、外部ライブラリなし（Composer 不使用） | 80サイトへの配布を zip 1つで済ませる。heteml/さくらの PHP で確実に動く |
| アーカイブ形式 | 独自ストリーミング ZIP ライタ（ZIP64、store/deflate 混在）+ バイト分割 | `ZipArchive` は close 時に全体を書き直すため大容量・中断再開に向かない。ZIP は復元時に誰でも開ける |
| DB ダンプ | `$wpdb` で純 PHP 実装 | `mysqldump` が使えない環境のため |
| pCloud API | `oauth2_token`、`userinfo`、`uploadfile`（multipart POST、`folderid` 指定）、`createfolderifnotexists`、`listfolder`、`renamefolder`、`deletefolderrecursive`、`checksumfile`（sha1 で照合）。認証は `Authorization: Bearer` ヘッダ | 公式ドキュメントに記載のある API のみ使う（未文書化の分割アップロード API は使わない）。`path` 指定は非推奨とされているため `folderid` を使う |
| HTTP クライアント | pCloud へのアップロードは PHP `curl` 拡張を直接使い `CURLFile` でストリーミング送信。それ以外の小さな API 呼び出しと GitHub への問い合わせは `wp_remote_get/post` | `WP_Http` はリクエストボディをメモリに全部載せるため、数十 MB のパート送信に向かない |
| 起点フォルダ | 公開ルート（5.3 の自動検出）。`ABSPATH` 固定にしない | サブフォルダ設置サイトのルート直下ファイルも含めるため |
| DB ダンプ範囲 | データベース内の全テーブル | DB 共有がない環境なので、プレフィックスなしのテーブルも漏らさない |
| 設定の優先順位 | `wp-config.php` の定数 > 管理画面の設定 > 既定値 | 80サイトの一括導入を楽にする |
| 配布と更新 | GitHub Releases から自動更新（12.1） | 80サイトへの手動配布を避ける |
| 状態保存 | 作業フォルダ内の `state.json`（原子的書き込み: 一時ファイル → `rename`） | DB に大きな状態を持たせない。ジョブ中断時の整合性 |
| 履歴 | `wp_options` に最新20件 | テーブル追加を避け、アンインストールを簡単にする |
| スケジュール計算 | 「最終成功時刻」ではなく「設定周期のグリッド」（例: 毎週なら前回予定 + 7日）で次回を決める | 遅延が蓄積しない |
| 国際化 | 日本語 UI を既定、`__()` で英語も用意 | 管理者は日本語話者 |
| アンインストール | オプション・作業フォルダ・cron イベントを削除。pCloud 上のバックアップは残す | 誤って消さない |

### 12.1 自動更新の仕組み（GitHub Releases）

依頼者の運用は「まず2〜3サイトで様子を見て、安定したら全サイトに展開」。その後の修正を80サイトに手で配らずに済むよう、初版から自動更新を組み込む。

- **配布元**: GitHub の公開リポジトリ（名前は `wp-pcloud-backup`。所有者アカウントは依頼者のもの。私の案として公開リポジトリとするが、非公開にしたい場合は `WP_PCLOUD_BACKUP_GITHUB_TOKEN` 定数でトークンを渡す方式を用意する）
- **リリース物**: リリースごとに `wp-pcloud-backup.zip`（プラグイン本体、フォルダ名 `wp-pcloud-backup/` 固定）と `wp-pcloud-backup.zip.sha256` を添付。リポジトリの `update.json`（最新バージョン・zip の URL・sha256 の URL・必要な WP/PHP バージョン・更新内容）をリリース時に更新する
- **リリース手順の自動化**: `bin/release.sh` を用意。バージョン番号を渡すとプラグインヘッダと `update.json` を書き換え、zip と sha256 を作り、git タグを打ち、`gh release create` でアップロードする
- **更新チェック**: プラグインは12時間ごとに `update.json` を `raw.githubusercontent.com` から取得（GitHub API のレート制限を避ける。heteml は多数のサイトが同じ IP を共有するため）。新しいバージョンがあれば WordPress 標準の更新機構（`pre_set_site_transient_update_plugins` フィルタ）に差し込み、プラグイン一覧に「更新があります」と出る
- **自動適用**: 設定「自動更新」が ON（既定）なら `auto_update_plugin` フィルタで true を返し、WordPress の自動更新（WP-Cron の `wp_version_check` 系イベント、通常12時間ごと）で無人適用される。OFF なら一覧から手動で更新
- **整合性**: ダウンロード後、インストール前に zip の SHA-256 を `.sha256` ファイルと照合（`upgrader_pre_install` フィルタ）。不一致なら中止し、通知メール `[WP pCloud Backup] 更新失敗: example.com` を送る
- **バックアップ実行中は更新しない**: ジョブが走っている間は自動更新を見送り、次のチェックで適用する（プラグインファイルの差し替えで実行中のランが壊れるのを防ぐ）
- **更新後**: 新バージョンの初回実行時に設定のマイグレーション（必要なら）を行い、履歴に「vX.Y.Z に更新」を記録する

## 13. 導入手順（80サイト分の運用）

1. 最初の1サイトで 5.1 の手順によりアクセストークンを取得し、控えておく
2. 各サイトの `wp-config.php` に `WP_PCLOUD_BACKUP_ACCESS_TOKEN` と `WP_PCLOUD_BACKUP_NOTIFY_EMAIL` を書く（SSH が使える heteml ではこれが最速。さくらは FTP またはファイルマネージャで編集。管理画面から貼り付けてもよい）
3. プラグイン zip をアップロードして有効化（heteml で WP-CLI が使えれば `wp plugin install <zipのURL> --activate`）。以後の更新は自動
4. 周期・世代数を変えたいサイトだけ設定を変更
5. さくらのサイト: WP-Cron を OFF にし、外部 cron 用 URL をコントロールパネルの cron に5分ごとで登録
6. 「今すぐバックアップ」で初回実行し、完走を確認
7. まず2〜3サイトで数週間運用し、安定したら残りのサイトへ展開

## 14. VPS 用スクリプト（区分 D）の概要

- `rclone` を pCloud リモートとして設定（rclone の pcloud バックエンドは OAuth 対応）
- 日次 cron:
  1. `mysqldump --single-transaction | gzip` → `/backup/db/YYYY-MM-DD.sql.gz`
  2. `rclone sync /var/www/site pcloud:WPBackup/bigsite.example.com/files --exclude ...`（変更分のみ転送）
  3. `rclone copy /backup/db pcloud:WPBackup/bigsite.example.com/db` + 古い DB ダンプの削除
  4. 失敗時は `mail` で通知
- 詳細設計はプラグイン完成後に別文書で

## 15. ビルダーに委ねる事項

- ストリーミング ZIP ライタの内部構造（ただし ZIP64 対応と、Mac の Finder・Windows エクスプローラー・`unzip` コマンドで開けることをテストで保証する）
- `state.json` のスキーマ
- 管理画面の AJAX 進捗表示の実装詳細
- 単体テストの構成（WP_Mock / PHPUnit いずれか）。少なくとも ZIP ライタと DB ダンプとスケジュール計算にはテストを書く
- 開発・検証用のローカル WordPress 環境（wp-env / Docker / Local など）
- ファイル名・クラス名の命名（プラグインスラッグは `wp-pcloud-backup`、PHP 名前空間は `WpPcloudBackup`）

## 16. 検証計画

- ローカル環境で 100MB / 3GB の模擬サイトを作り、処理時間上限 20 秒で完走すること
- 意図的に中断（プロセス kill、pCloud 応答エラーの模擬）して再開できること
- 生成した分割 ZIP を結合・展開し、元ファイルと SHA-256 が一致すること
- DB ダンプを別 DB に流し込み、テーブル数・行数が一致すること
- 世代数を超えた古いフォルダが削除され、未完了フォルダは数えられないこと
- 外部 cron 用 URL の鍵不一致で何も起きないこと
- WordPress をサブフォルダに置いた構成で、ドメイン直下のファイルが ZIP に含まれること
- 25MB パートの送信が、PHP の `max_execution_time=30` と `memory_limit=128M` の環境で成功すること
- 旧バージョンを入れたテストサイトで、GitHub のリリースを公開すると自動更新が適用されること。sha256 を改ざんしたリリースでは更新が中止され通知が届くこと
- heteml の実サイト1つ、さくらの実サイト1つで本番検証してから全サイトに展開
